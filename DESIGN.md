# FishEye — Frontend Design System & Implementation Specification

> **Version:** 1.0 · **Status:** Required frontend specification for MVP · **Updated:** 2026-10-21  
> **Scope:** `apps/web/landing`, `apps/web/console`, `packages/ui` and any frontend generated by Codex.  
> **Read with:** [BRAND.md](./BRAND.md), [PRD.md](./PRD.md), [ARCHITECTURE.md](./ARCHITECTURE.md), [AGENTS.md](./AGENTS.md).  
> **Design reference:** [FishEye Figma](https://www.figma.com/design/6ltsfIACCq14P4GQMbssi6). Figma expresses design intent; this document defines implementable invariants. Do not assume current static screens are clickable/responsive without engineering verification.

## 1. Design goal

FishEye is an **evidence-first investigation interface**, not an animated marketing dashboard or a mock security operations center. It helps an analyst answer three questions quickly:

1. **Which findings need my attention?**
2. **Why did the detector flag this account?**
3. **Does this detector reduce false alarms without missing threats?**

A restrained visual system is a functional requirement: low noise, consistent information hierarchy, readable comparisons, honest uncertainty and obvious actions.

**Non-negotiable identity:** Light-only, black and white with neutral gray; Inter everywhere; no purple, dark surfaces, ornamental neon/glow effects in UI, gradient cards or colored risk chips. The anglerfish *logo bulb* can have a subtle grayscale halo in its brand asset only.

**Do not treat the design system as permission to invent features.** The PRD governs product scope.

## 2. Source-of-truth order

For frontend work, use these sources in order:

1. **PRD.md:** required screens, states, flows, acceptance criteria and evidence labeling.
2. **BRAND.md:** FishEye identity, approved logos, tone, color restrictions, typography.
3. **DESIGN.md:** UI tokens, component rules, layout and accessibility.
4. **Current FishEye Figma pages:** concrete visual composition and spacing inspiration.
5. **Current shared UI code:** verified implementation details, but not authority to contradict above.

If Figma conflicts with product truth, choose correctness and request design reconciliation. Archive/legacy Sentinel pages are **not** current design references.

## 3. Architecture and ownership

- `apps/web/landing`: Astro, primarily static; use React islands only for genuine interaction.
- `apps/web/console`: Next.js App Router + React + TypeScript; all protected data and business decisions originate in FastAPI through the typed API contract. Use the Next.js server runtime for request-time authentication and rendering.
- `packages/ui`: FishEye tokens, primitives and shared components; avoid excessive coupling to Astro/Next.js routing or server-runtime details.
- `packages/api-client`: generated from OpenAPI; do not copy API response types into individual screens.
- Use Tailwind CSS with a single shared token configuration; no repeated hardcoded colors and spacing for the same patterns.
- Use TanStack Query for server state, TanStack Table for investigation lists, Recharts where comparisons genuinely help.
- **Never calculate authoritative detector scores, severity or research metrics in UI**. Format server results; never replace unavailable data with visually believable invented numbers.

### Next.js console boundary

Use Next.js App Router server components for request-time page assembly and protected initial reads; client components for filtering, charts, local interactions and polling. Prefer explicit server-to-FastAPI requests and server-validated sessions. TanStack Query is appropriate where client-side refetching/polling is required, but do not duplicate fetched server state without a reason. Avoid routing protected FastAPI domain logic into Next.js Route Handlers or Server Actions. Do not choose `output: "export"` for the authenticated console.

## 4. Foundation tokens

Start with named semantic tokens in `packages/ui`, then bind them to Tailwind/CSS variables and document aliases. Prefer interoperable design-token notation; the Design Tokens Community Group specification provides a shared format but does **not** mandate FishEye values.

### Color tokens (single light theme)

| Semantic token | Hex | Rules |
| --- | --- | --- |
| `--fe-bg` | `#FFFFFF` | Main canvas; always light |
| `--fe-surface` | `#FFFFFF` | Cards, popovers and dialogs |
| `--fe-surface-muted` | `#F7F7F7` | Sidebar, table headings, alternate rows |
| `--fe-surface-hover` | `#EEEEEE` | Hover/selection where needed |
| `--fe-ink` | `#111111` | Primary text, solid actions |
| `--fe-text-secondary` | `#595959` | Supporting copy, subtitles |
| `--fe-text-subtle` | `#666666` | Quiet labels, metadata, verified AA on white |
| `--fe-border` | `#D7D7D7` | Structural borders (nonessential separators) |
| `--fe-border-strong` | `#858585` | Important control boundaries |
| `--fe-text-inverse` | `#FFFFFF` | Primary action label on ink |
| `--fe-focus` | `#111111` | Visible keyboard focus outline |

No second theme; do not add `dark:` Tailwind utilities or theme toggles. Respect forced-colors/high-contrast user preferences with accessible native behavior even though the brand has no dark mode.

**Contrast gates:** AA body text >= 4.5:1; large text >= 3:1; meaningful UI component boundaries and graphics >= 3:1 against adjacent surfaces where applicable. Explicitly validate control outlines and secondary text against their actual backgrounds. Do not assume `--fe-border` meets non-text contrast for critical inputs; use `--fe-border-strong` where needed.

### Typography

Use locally delivered or properly loaded **Inter** with `font-display: swap`; define a controlled system-sans fallback. Keep line-height and wrap stable.

| Role | Suggested desktop default | Weight | Line height |
| --- | --- | --- | --- |
| Marketing hero | 56–68 px, responsive | 700 | 1.08–1.14 |
| Product page heading | 28–32 px | 700 | 1.2 |
| Section heading | 18–22 px | 600 | 1.3 |
| Body | 14–16 px | 400 | 1.5 |
| Navigation | 14 px | 500 / 600 | 1.4 |
| Label / table | 12–14 px | 500 / 600 | 1.35–1.5 |
| Metric | 28–36 px | 700 | 1.15 |
| Fine print | Prefer >= 12 px | 400 | 1.5 |

Avoid all-caps for substantial prose; use sentence case in navigation, headings and actions. Use `font-variant-numeric: tabular-nums` for metrics, table quantities and deltas. Do not truncate evidence explanations that contain crucial meaning; expand/collapse with accessible labels if necessary.

### Spacing, radius, layout

Use 4 px base increments, with a constrained scale `4, 8, 12, 16, 24, 32, 40, 48, 64, 80` px. Named sizes should be reusable CSS variables/Tailwind tokens, not arbitrary values.

- Default control heights: 40–44 px; small dense controls only where accessibility permits.
- Standard horizontal page padding: desktop 32–40 px, tablet 24 px, mobile 16 px.
- Cards: 12 px radius, 1 px border, 20–24 px inner padding; shadows optional and extremely restrained.
- Buttons/inputs: 8 px radius; pills 999 px where labels are short and compact.
- Sidebar: approximately 232–240 px, persistent on sufficiently wide desktop only.
- Desktop content: allow dashboard density without crowding; establish max-readable-width for prose pages (~1100–1200 px).
- Transitions: short and utilitarian (around 120–180 ms) where used; respect `prefers-reduced-motion`.

These are **initial design decisions**. Verify against the Figma compositions and real device testing before freezing component values.

## 5. Responsive behavior

Treat 1440 px desktop frames as **reference**, not a requirement that mobile visitors horizontally scroll.

- **Wide desktop (>= 1200px):** persistent sidebar and multi-column metrics/cards.
- **Compact desktop/tablet (~768–1199px):** sidebar collapses to an accessible navigation drawer or narrow rail; comparison panels stack as needed.
- **Mobile (< 768px):** single-column layout, menu button + drawer, full-width actions; cards stack.
- Investigation tables with genuinely many columns may use a clearly labeled horizontally scrollable table region or an accessible row-summary pattern; preserve identifiers and score, never silently hide essential evidence.
- Modal/dialog dimensions must fit viewport with internal scroll; focus stays managed.
- Test 320, 375, 768, 1024 and 1440 px widths at minimum, plus 200% browser zoom/reflow.

Breakpoint values are implementation choices and may be tuned after review, but screen meaning and actions must remain equivalent.

## 6. Shared component inventory and required states

Implement reusable components with typed props and behavior documentation, not screen-specific copies.

| Component | Required states / rules |
| --- | --- |
| `BrandLogo` | `mark`, `wordmark`, `combined`; proportional scaling and safe alt labels |
| `AppShell` / `Sidebar` | Active route, collapsed nav, keyboard navigation, mobile drawer |
| `Button` | Primary, secondary, ghost; hover, focus-visible, disabled, loading |
| `Input` / `Select` | Label, help, required, invalid, focus, disabled; visible errors |
| `Card` / `MetricCard` | Label, unit, source/run context, loading and unavailable value |
| `SeverityLabel` | Low/Medium/High **as explicit text** with monochrome border/weight differences |
| `FindingTable` | Server pagination, sorting, empty/loading/error states, accessible headers |
| `EvidenceList` / `EventTimeline` | Event IDs, UTC/display time, signal and baseline context |
| `ReviewForm` | Decision options, note field, submission/pending/conflict/success |
| `RunStatus` | Queued/running/completed/failed; bounded polling or refresh |
| `MetricComparison` | Three detectors; precision/recall/FPR, counts, methodology notes |
| `StatePanel` | Empty, loading, error, unauthorized, no access, retry and completion |
| `Dialog` / `Toast` | Correct focus/announcement semantics and no color-only meaning |

Use existing accessible primitives when warranted; do not build custom combobox/dialog behavior without keyboard and screen-reader testing. Avoid gratuitous abstraction before shared usage is established.

### Component documentation rule

Each shared component should document purpose, usage/non-usage, variants, props, behavior, keyboard interaction, responsive constraints, empty/error/loading states, design token bindings, and a test/example. This structure follows mature design-system practice—not a requirement to build an enormous component library before screens.

## 7. Page specifications

### 7.1 Landing (`apps/web/landing`)

**Goal:** Explain one problem and one promise within seconds.

Suggested hierarchy:
1. Header with **combined FishEye logo**, concise navigation and a single CTA.
2. Hero: **“Not every unusual action is a threat.”**
3. One explanatory sentence: contextual review helps analysts focus on meaningful signals.
4. Primary CTA (“Explore the product”), optional secondary research/method link.
5. Three compact steps: understand behaviour, prioritize findings, evaluate outcomes.
6. Footer with the **synthetic research-stage disclaimer**.

No long feature grid, testimonial logos, fabricated statistics, stock photography, pricing or decorative cybersecurity imagery. SEO/semantic structure: one H1, meaningful page title/description, clean landmark tags and descriptive links. Astro should ship minimal JS.

### 7.2 Authentication (`/login`)

Official logo, short introduction and safe authentication flow. Form fields have visible labels, not placeholder-only labels. Show field and auth errors discreetly without exposing account enumeration details. Never display hardcoded real-looking credentials or claim an actual bank login.

### 7.3 Overview (`/overview`)

At-a-glance account/window counts, flagged findings, High-priority count and selected run context. Then a **prioritized evidence table**. The source of every score/count is a completed backend run. Provide explicit empty/zero states and run selection; synthetic badges/disclaimers must stay visible.

### 7.4 Investigations (`/investigations`, `/:id`)

Findings list with server-side filters/sort/pagination. Detail page displays account, severity, score, detector/run version, concise narrative reason, signal-by-signal evidence and time-ordered event references. Review action is explicit and separate from model output. No irreversible security action in v1.

### 7.5 Scenario lab (`/scenarios`)

Select a **versioned predefined synthetic** scenario/dataset; view its description and constraints; start a run. Return a real run ID, status and link to results. Do not render canned success as if backend computation completed. Disable conflicting duplicate submissions and expose recoverable failure states.

### 7.6 Evaluation (`/evaluation`)

Compare **simple rules**, **tuned rules** and **FishEye contextual scoring** from the same run/dataset. Show precision, recall, false-positive rate, alert burden, delay, confusion matrix and missed-threat examples. Charts support tables, not replace them. Label units, denominators, test conditions and synthetic limitations; undefined metrics must read **“Not defined”** with explanation, never `0%` or `100%` by convenience.

## 8. Investigation-specific interaction rules

- **Priority != guilt:** Render “High priority” rather than “Attacker confirmed.”
- **Evidence before opinion:** Show recorded synthetic events and comparison context above any summarized interpretation.
- **Context matters:** Timestamp only has meaning with timezone and expected working pattern; role signal must indicate the permission comparison.
- **Explain outcomes:** Each reason code should have a concise plain-language explanation and a way to inspect the underlying value/baseline.
- **Consistency:** Queue, detail and exported reports must show the same stored score and tier for the same run and finding.
- **Review audit:** A reviewer can mark a finding benign/escalated; that operation must not rewrite detector results.
- **No fake live badges:** Avoid “Monitoring live” and “Protected bank” unless operationally true.
- **Uncertainty:** Show “insufficient history” and cold-start situations clearly rather than inventing confidence.

## 9. Tables, charts and data display

- Prefer accessible native table markup for event/finding data. Set `scope` on headers, add useful table captions/labels, announce sorting changes, preserve reading order and keyboard focus.
- Server pagination controls must expose current page/total if available and remain operable with assistive tech.
- Right-align comparable numeric table cells, preserve precision consistently, use tabular numerals and explicit units.
- Charts: use black/gray stroke and pattern/marker variation, not color. Add meaningful legends, axes and text alternative/data table. Avoid truncated axes that imply false improvements.
- A risk score is dimensionless; metrics such as FPR and precision are percentages or ratios. Never conflate them.
- Pending, incomplete or failed runs must not populate charts as final data.

## 10. Interaction and accessibility acceptance

Target **WCAG 2.2 AA** as the frontend acceptance baseline:

- Sufficient text and non-text contrast; readable states and charts.
- Visible keyboard focus on every actionable control.
- Correct label-to-control association, field-level validation and screen-reader announcements.
- Escape closes dismissible overlays; focus returns to the trigger, and modal focus is managed.
- Descriptive button text, table semantics and accessible sort/filter controls.
- Do not rely only on color, position, animation or icon shape to communicate severity/status.
- Support zoom/reflow, motion reduction and high-contrast assistive settings.
- Use semantic HTML before ARIA workarounds. Automated checks assist but do not replace keyboard/screen-reader review.

## 11. Figma-to-code workflow for Codex

Before building a screen:

1. Read [PRD.md](./PRD.md), [BRAND.md](./BRAND.md), this file and the target Figma frame.
2. Inspect existing `packages/ui` components/tokens and create missing primitives at the shared boundary.
3. Identify the screen's real API data, interactions, empty/error/loading states and mobile layout.
4. Implement structural semantics and functional data binding **before** pixel polish.
5. Match Figma spacing/type/layout while correcting unsupported or inaccessible mock content.
6. Review at target desktop and responsive widths; compare screenshot/rendered UI against Figma.
7. Test keyboard, important screen-reader semantics and contrast, and run applicable TS/lint/build tests.
8. State what was tested, what is still a visual approximation, and what remains unfinished.

**Design parity gate:** Don't label a screen finished because its desktop screenshot looks similar. It must respond correctly to true API states and preserved evidence semantics.

## 12. Change control and release QA

Any visual token change must be made in the **shared token source**, reflected in design documentation and reviewed on representative landing, sign-in, overview, detail and evaluation surfaces. Use small, reviewable PRs.

**Per-screen definition of done:**
- [ ] Uses canonical FishEye logos, Inter and grayscale light palette only.
- [ ] Matches information hierarchy and product truth.
- [ ] Functional route, data source and access control.
- [ ] Loading/empty/error/unauthorized paths implemented.
- [ ] Keyboard/focus/contrast/table accessibility reviewed.
- [ ] Responsive across supported widths and zoom.
- [ ] Metrics and scores bound to real completed API results.
- [ ] Shared components and design tokens reused.
- [ ] Tests/build pass or documented blockers explicitly reported.
